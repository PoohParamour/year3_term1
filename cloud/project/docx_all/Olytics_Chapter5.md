## บทที่ 5

## สรุปผลการดำเนินงาน

### 5.1 ที่มาและการทำงานโดยรวมของระบบ

Olytics เป็นระบบคลังข้อมูล (Data Warehouse) บนระบบคลาวด์ AWS ที่พัฒนาขึ้นเพื่อรองรับการวิเคราะห์ข้อมูลธุรกิจอีคอมเมิร์ซจากชุดข้อมูล Olist (Brazilian E-Commerce) โดยมีจุดประสงค์หลักคือจำลองกระบวนการนำเข้าข้อมูล (Ingestion) ที่ทยอยเข้ามาอย่างต่อเนื่อง แล้วประมวลผลผ่านขั้นตอน ETL (Extract, Transform, Load) โดยอัตโนมัติ ตั้งแต่การตรวจจับไฟล์ใหม่ใน Amazon S3 การทำความสะอาดข้อมูลด้วย AWS Glue DataBrew การแปลงข้อมูลให้อยู่ในรูปแบบ Star Schema ด้วย AWS Glue ETL Job ไปจนถึงการจัดเก็บข้อมูลที่ผ่านการแปลงแล้วลงใน Amazon Redshift เพื่อใช้เป็นคลังข้อมูลหลักสำหรับการสืบค้น

ผลลัพธ์สุดท้ายของระบบถูกนำเสนอผ่านเว็บแอปพลิเคชัน Dashboard ที่พัฒนาด้วย Next.js และ Node.js ซึ่งสืบค้นข้อมูลจาก Amazon Redshift มาแสดงผลในรูปแบบกราฟและตารางสรุปเชิงธุรกิจ โดยเว็บแอปพลิเคชันถูกวางไว้ใน Public Subnet และ Redshift ถูกวางไว้ใน Private Subnet ภายใน Amazon VPC เดียวกัน เพื่อจำกัดการเข้าถึงคลังข้อมูลโดยตรงจากอินเทอร์เน็ต

### 5.2 ประโยชน์ของระบบ

- ช่วยให้เห็นภาพรวมของกระบวนการสร้างคลังข้อมูลตั้งแต่ต้นจนจบ (End-to-End Data Pipeline) บนสภาพแวดล้อมคลาวด์จริง ไม่ใช่การจำลองบนเครื่องส่วนตัว
- ลดการทำงานซ้ำซ้อนที่ต้องทำด้วยมือ เนื่องจากกระบวนการ ETL ทำงานอัตโนมัติทันทีที่มีไฟล์ข้อมูลใหม่เข้ามาใน S3
- ข้อมูลที่ผ่านการแปลงแล้วถูกจัดเก็บในรูปแบบ Star Schema ทำให้สืบค้นและวิเคราะห์เชิงธุรกิจ (เช่น ยอดขายตามช่วงเวลา ระยะเวลาจัดส่ง ความพึงพอใจลูกค้า) ได้รวดเร็วกว่าการสืบค้นจากข้อมูลดิบโดยตรง
- Dashboard ช่วยให้ผู้ใช้งานที่ไม่มีพื้นฐานด้าน SQL สามารถเข้าใจข้อมูลเชิงลึกของธุรกิจได้ง่ายขึ้นผ่านการแสดงผลเชิงภาพ
- สถาปัตยกรรมแบบแยกส่วน (S3 → Lambda → Glue → Redshift → Dashboard) ทำให้ทีมเข้าใจบทบาทของแต่ละบริการ AWS อย่างชัดเจน และนำแนวคิดไปประยุกต์ใช้กับโปรเจกต์ data pipeline อื่นได้ในอนาคต

### 5.3 ปัญหาและอุปสรรคที่เกิดขึ้นในการพัฒนา

> ⚠️ หัวข้อนี้ต้องแก้ให้ตรงกับปัญหาที่ทีมเจอจริงระหว่างทำโปรเจกต์ ผมร่างตัวอย่างที่ "น่าจะเกิดขึ้นได้จริง" จากข้อจำกัดของ AWS Academy Learner Lab ที่ใช้งานไว้ให้เป็นแนวทาง — ไม่ใช่เหตุการณ์ที่ยืนยันว่าเกิดขึ้นจริงกับทีมนี้

- ข้อจำกัดของ AWS Glue ใน Learner Lab ที่รองรับ Concurrency สูงสุดเพียง 1 งานในเวลาเดียวกัน ทำให้ไม่สามารถทดสอบหลาย ETL Job พร้อมกันได้ ต้องวางแผนลำดับการรันงานให้ดีก่อนทดสอบ
- Session ของ Learner Lab มีเวลาจำกัดและงบประมาณคงที่ต่อโมดูล ทำให้ต้องปิด/เริ่มการทำงานของบริการต่างๆ (เช่น Redshift, EC2) อย่างระมัดระวังเพื่อไม่ให้งบหมดก่อนโปรเจกต์เสร็จ
- การตั้งค่า IAM ทำได้จำกัดเพราะต้องใช้ LabRole ที่มีอยู่แล้วเท่านั้น ไม่สามารถสร้าง Role หรือกำหนดสิทธิ์แบบละเอียดเองได้ ทำให้ต้องปรับการออกแบบสิทธิ์การเข้าถึงให้สอดคล้องกับสิทธิ์ของ LabRole แทน
- การเชื่อมต่อระหว่าง Amazon EC2 (Dashboard) กับ Amazon Redshift ที่อยู่ใน Private Subnet ต้องตั้งค่า Security Group และ Subnet ให้ถูกต้องจึงจะสื่อสารผ่านพอร์ต 5439 ได้ ซึ่งต้องใช้เวลาศึกษาและทดลองหลายรอบกว่าจะเชื่อมต่อได้สำเร็จ
- ทีมมีเวลาจำกัดเนื่องจากต้องแบ่งเวลาไปจัดการวิชาอื่นร่วมด้วย ส่งผลให้การทดสอบและปรับแต่งบางส่วนทำได้ไม่ครบถ้วนเท่าที่ควร

### 5.4 ข้อจำกัดของระบบ

เนื่องจากระบบพัฒนาอยู่ภายใต้สภาพแวดล้อม AWS Academy Learner Lab ซึ่งมีข้อจำกัดเฉพาะที่แตกต่างจากบัญชี AWS ทั่วไป ระบบจึงมีข้อจำกัดดังนี้ (สรุปย่อจากข้อจำกัดที่ระบุไว้แล้วในบทที่ 1 หัวข้อ 1.3.4 — ถ้าเนื้อหาในบทที่ 1 มีการแก้ไขเพิ่มเติม ให้ปรับหัวข้อนี้ให้ตรงกัน):

- ใช้งานได้เฉพาะ Region us-east-1 และ us-west-2 เท่านั้น
- Amazon Redshift รองรับเฉพาะ Instance type ra3.large และจำกัดคลัสเตอร์สูงสุด 2 instance
- Amazon EC2 รองรับ Instance type nano–large เท่านั้น และจำกัดไม่เกิน 9 instance ที่รันพร้อมกัน (รวมไม่เกิน 32 vCPU)
- AWS Glue จำกัด Worker สูงสุด 10 และ Concurrency สูงสุด 1 งานต่อครั้ง
- ไม่สามารถสร้าง IAM Role หรือกำหนดสิทธิ์แบบกำหนดเองได้ ต้องใช้ LabRole ที่ระบบเตรียมไว้ให้เท่านั้น
- บัญชีมีงบประมาณจำกัดต่อโมดูล และ Session จะหมดอายุเมื่อครบเวลาที่กำหนด ต้องปิดทรัพยากรที่ไม่ใช้งานอยู่เสมอเพื่อประหยัดงบ
- ระบบปัจจุบันออกแบบมาให้รองรับการทำงานพื้นฐานของ pipeline เท่านั้น หากต้องการขยายฟีเจอร์ในอนาคต (เช่น การแจ้งเตือนแบบ Real-time เพิ่มเติม หรือการวิเคราะห์เชิงลึกมากขึ้น) จะต้องมีการจัดการบริการเพิ่มเติม ซึ่งอาจส่งผลให้ค่าใช้จ่ายในการใช้งาน AWS เพิ่มขึ้น

### 5.5 ประมาณการค่าใช้จ่าย

เนื่องจากโปรเจกต์นี้พัฒนาบนสภาพแวดล้อม AWS Academy Learner Lab ซึ่งเป็น Sandbox ที่กำหนดงบประมาณคงที่ไว้ล่วงหน้าต่อโมดูล (ไม่ใช่การเรียกเก็บเงินแบบบัญชี AWS ทั่วไปที่คิดตามการใช้งานจริงรายบริการ) การประมาณค่าใช้จ่ายของระบบจึงอ้างอิงจากยอดการใช้งบประมาณสะสมที่แสดงในหน้า Learner Lab โดยตรง แทนการแจกแจงค่าใช้จ่ายรายบริการผ่าน AWS Cost Explorer เหมือนบัญชี AWS ทั่วไป

**[แนบรูปที่ 5.1 ตรงนี้ — ใช้ screenshot หน้า AWS Academy Learner Lab ที่ส่งมา (แถบแสดง "Used $16.3 of $50")]**

> รูปที่ 5.1 ภาพรวมการใช้งบประมาณในสภาพแวดล้อม AWS Academy Learner Lab

จากรูปที่ 5.1 พบว่าระบบใช้งบประมาณไปแล้ว **16.3 ดอลลาร์สหรัฐ จากงบประมาณทั้งหมด 50 ดอลลาร์สหรัฐ** ที่ได้รับจัดสรรต่อโมดูล คิดเป็นประมาณ 32.6% ของงบประมาณทั้งหมด ซึ่งเกิดจากการใช้งานบริการหลักของระบบตลอดช่วงพัฒนาและทดสอบ ได้แก่ Amazon Redshift (คลัสเตอร์คลังข้อมูล), Amazon EC2 (เซิร์ฟเวอร์โฮสต์เว็บแอปพลิเคชัน Dashboard), AWS Glue (งาน ETL และ DataBrew) และ Amazon S3 (พื้นที่จัดเก็บข้อมูล Raw และ Curated Zone)

> หมายเหตุ: ถ้าทีมมี screenshot หน้า Cost Explorer ที่แจกแจงค่าใช้จ่ายแยกตามบริการ (Group by Service) เพิ่มเติม สามารถแนบเป็นรูปที่ 5.2 ต่อท้ายได้ เพื่อให้เห็นว่าบริการใดใช้งบประมาณมากที่สุด แต่ถ้าไม่มีข้อมูลนี้ หัวข้อนี้ใช้แค่รูปที่ 5.1 ก็เพียงพอ ไม่จำเป็นต้องมี

### 5.6 การวิเคราะห์และออกแบบเพิ่มเติมโดยไม่คำนึงถึงค่าใช้จ่าย

เนื่องจาก Olytics ถูกพัฒนาภายใต้ข้อจำกัดด้านงบประมาณและบริการของ AWS Academy Learner Lab หากไม่มีข้อจำกัดดังกล่าว ระบบสามารถขยายขีดความสามารถเพิ่มเติมได้ดังนี้

1. **ปรับปรุงด้านการแสดงผลเชิงธุรกิจ**
   - Amazon QuickSight : ใช้แทนหรือเสริมการแสดงผลที่พัฒนาเองบน Dashboard เพื่อให้ผู้ใช้งานที่ไม่ใช่สายเทคนิคสามารถสร้างรายงานและ Dashboard ของตนเองได้ (บริการนี้ไม่รองรับใน Learner Lab)

2. **ขยายขีดความสามารถของคลังข้อมูล**
   - Amazon Redshift : เพิ่มจำนวนโหนดหรือเปลี่ยนเป็น Instance type ที่ใหญ่ขึ้นกว่า ra3.large เพื่อรองรับข้อมูลปริมาณมากขึ้นและสืบค้นได้เร็วขึ้น
   - Redshift Serverless : เปลี่ยนรูปแบบคลังข้อมูลให้ปรับขนาดอัตโนมัติตามปริมาณงาน ลดภาระการจัดการคลัสเตอร์

3. **เพิ่มความปลอดภัยของระบบ**
   - สร้าง IAM Role และกำหนดสิทธิ์แบบละเอียด (Least Privilege) เฉพาะแต่ละบริการ แทนการใช้ LabRole ร่วมกันทั้งระบบ
   - AWS WAF : ป้องกันการโจมตีเว็บแอปพลิเคชัน Dashboard จากอินเทอร์เน็ต
   - NAT Gateway : ให้ทรัพยากรใน Private Subnet เชื่อมต่อออกอินเทอร์เน็ตได้อย่างปลอดภัยโดยไม่เปิดเผยที่อยู่ IP โดยตรง

4. **เพิ่มความพร้อมใช้งานและประสิทธิภาพของเว็บแอปพลิเคชัน**
   - Elastic Load Balancing และ Auto Scaling : กระจายโหลดและปรับจำนวน EC2 Instance อัตโนมัติตามปริมาณผู้ใช้งาน แทนการใช้ EC2 เพียง instance เดียว
   - Amazon CloudFront : ใช้เป็น CDN เพื่อลด Latency ในการเข้าถึง Dashboard จากผู้ใช้งานในพื้นที่ต่างๆ

5. **ขยายขอบเขตการวิเคราะห์ข้อมูล**
   - Amazon SageMaker : เพิ่มชั้นการวิเคราะห์เชิงพยากรณ์ (เช่น พยากรณ์ยอดขายหรือความล่าช้าในการจัดส่ง) ต่อยอดจากข้อมูลใน Star Schema ที่มีอยู่แล้ว ซึ่งเป็นแนวทางที่เคยพิจารณาไว้ตั้งแต่ขั้นวางแผนโครงการ แต่ตัดออกจากขอบเขตเนื่องจากข้อจำกัดด้านเวลาและทรัพยากร

ทั้งนี้แนวทางข้างต้นเป็นแนวทางเพื่อการต่อยอดในอนาคต มิได้อยู่ในขอบเขตของระบบที่พัฒนาในโครงการนี้
