# ส่วนที่ 1 — บทที่ 1: บทนำ (5 สไลด์)

## สไลด์ 2 — ที่มาและปัญหา

**เนื้อหา (สรุปจาก 1.1 ทั้งหมดให้เหลือสไลด์เดียว):**
- E-Commerce โตเร็ว → ข้อมูลมหาศาลทุกวัน (คำสั่งซื้อ/สินค้า/ลูกค้า/ผู้ขาย/ชำระเงิน/รีวิว) แต่กระจัดกระจายในระบบ Transactional ที่ไม่เหมาะกับการวิเคราะห์เชิงลึก
- Data Warehouse คือทางออก แต่แบบ on-premise ลงทุนฮาร์ดแวร์สูง + ดูแลต่อเนื่อง
- ข้อมูลจริงเข้ามาต่อเนื่อง → ต้องออกแบบให้นำเข้าอัตโนมัติ ลดงานมือ

**หมายเหตุการออกแบบ:** ใช้เป็น 1 สไลด์ ไม่ต้องแยกย่อหน้าเหมือนรายงาน

## สไลด์ 3 — แนวคิดโครงงาน + วัตถุประสงค์

**เนื้อหา:**
- พัฒนาระบบคลังข้อมูลบน **AWS** ใช้ข้อมูลจริง **Olist** (บราซิล) กว่า **100,000 คำสั่งซื้อ** (2016–2018)
- วัตถุประสงค์ (1.2, ย่อ 6 ข้อ):
  1. ออกแบบสถาปัตยกรรม Data Warehouse บนคลาวด์
  2. พัฒนา ETL แปลงข้อมูลเป็น Star Schema
  3. ศึกษา ETL Pipeline แบบอัตโนมัติ
  4. แสดงว่าจัดการข้อมูลใหญ่ได้โดยไม่ต้องมีฮาร์ดแวร์จริง
  5. เปรียบเทียบ Athena vs Redshift
  6. นำเสนอผลวิเคราะห์ผ่าน Dashboard

**หมายเหตุการออกแบบ:** รวมแนวคิด+วัตถุประสงค์ในสไลด์เดียวเพื่อประหยัดเวลา

## สไลด์ 4 — ขอบเขตของระบบ: ฟังก์ชันหลัก

**เนื้อหา (1.3.1-1.3.2 รวมกัน):**
- เป้าหมาย: จัดการวงจรข้อมูลอีคอมเมิร์ซครบวงจร — นำเข้า → ทำความสะอาด → แปลง → จัดเก็บ → แสดงผล
- 7 ฟังก์ชันหลัก: นำเข้าข้อมูลดิบ (จาก Database) / ตรวจจับ+สั่งงานอัตโนมัติ / ทำความสะอาดข้อมูล / แปลงสู่ Star Schema / จัดเก็บคลังข้อมูล / สืบค้นเปรียบเทียบ Athena-Redshift / แสดงผล Dashboard

**หมายเหตุการออกแบบ:** ใส่ไดอะแกรมสถาปัตยกรรม (ที่ทำใน Lucid) แทนการไล่ bullet 7 ข้อ — จะไปลงรายละเอียดเต็มอีกทีในสไลด์บทที่ 3

## สไลด์ 5 — ข้อจำกัดของระบบ

**เนื้อหา (1.3.4 สรุปย่อ 9→4 กลุ่ม):**
- Region จำกัด (us-east-1, us-west-2 เท่านั้น)
- ขนาด resource จำกัด: Glue (Worker ≤10, Concurrency 1), Redshift (ra3.large, ≤2 instance), Lambda (≤10 concurrent), EC2 (nano-large, ≤9 instance)
- สร้าง IAM ใหม่ไม่ได้ (LabRole เท่านั้น), ไม่มี QuickSight → ต้องสร้างเว็บ Dashboard เอง
- งบประมาณจำกัด, เน้น Batch ไม่ใช่ Real-time, ข้อมูล ~100,000 รายการ

**หมายเหตุการออกแบบ:** จัดเป็น grid สั้น ๆ ไม่ต้องอ่านครบทุกข้อ เน้นให้ อ. เห็นว่าทำงานภายใต้ AWS Academy Learner Lab

## สไลด์ 6 — ประโยชน์ที่คาดว่าจะได้รับ

**เนื้อหา (1.4 จัดกลุ่ม 8→3 ธีม):**
- **เทคนิค:** ระบบคลังข้อมูลที่ใช้งานได้จริง, เข้าใจ Star Schema และ ETL Pipeline บนคลาวด์
- **ธุรกิจ:** insight เชิงธุรกิจ (ยอดขาย/สินค้ายอดนิยม/ความสัมพันธ์เวลาจัดส่ง-รีวิว), เข้าใจ Serverless vs คลังข้อมูลเฉพาะทาง
- **ทีม:** ประสบการณ์วางแผนและทำงานร่วมกัน

**หมายเหตุการออกแบบ:** ปิดท้ายบทที่ 1 สั้น ๆ แล้วเปลี่ยนไปบทที่ 2

# ส่วนที่ 2 — บทที่ 2: ทฤษฎีและเทคโนโลยีที่เกี่ยวข้อง (6 สไลด์)

## สไลด์ 7 — ภาพรวมธุรกิจ E-commerce

**เนื้อหา (สรุปหัวข้อ 1.1-1.5 ของบทที่ 2):**
- E-commerce = ซื้อขายผ่านอินเทอร์เน็ต เข้าถึงลูกค้าได้กว้างขึ้น ไม่จำกัดสถานที่/เวลา
- ข้อมูลหลักที่ต้องจัดการ: **สินค้า** (ราคา/สต็อก) / **ลูกค้า** (พฤติกรรม/ประวัติซื้อ) / **คำสั่งซื้อ** (สถานะ/การจัดส่ง)
- ข้อมูลเหล่านี้นำมาวิเคราะห์ธุรกิจได้ (ยอดขาย สินค้าขายดี พฤติกรรมลูกค้า) แต่ถ้าใช้ Operational Database ตรง ๆ วิเคราะห์ยาก → ต้องใช้ **Data Warehouse**

**หมายเหตุการออกแบบ:** สไลด์นี้เป็นสะพานเชื่อมไปสู่แนวคิด Data Warehouse ในสไลด์ถัดไป ไม่ต้องลงรายละเอียดทุกหัวข้อย่อย

## สไลด์ 8 — แนวคิดคลังข้อมูล (Data Warehouse)

**เนื้อหา (หัวข้อ 2, 2.1 ของบทที่ 2):**
- นิยาม: ระบบรวบรวมข้อมูลจากหลายแหล่ง ผ่าน **ETL** แล้วจัดเก็บให้เหมาะกับการวิเคราะห์
- คุณลักษณะ 4 ข้อ:
  1. **Subject-Oriented** — จัดตามหัวข้อที่วิเคราะห์ (ลูกค้า/สินค้า)
  2. **Integrated** — รวมจากหลายแหล่ง มาตรฐานเดียวกัน
  3. **Time-Variant** — เก็บข้อมูลย้อนหลัง วิเคราะห์แนวโน้มได้
  4. **Non-Volatile** — ข้อมูลไม่ถูกแก้/ลบ เพิ่มต่อเนื่อง

**หมายเหตุการออกแบบ:** ใช้ไอคอน/กราฟิก 4 ช่องสำหรับ 4 คุณลักษณะ

## สไลด์ 9 — องค์ประกอบระบบคลังข้อมูล + ETL

**เนื้อหา (หัวข้อ 2.2, 3 ของบทที่ 2):**
- Data Warehouse Architecture 4 ส่วน: **Data Source → ETL Process → Data Warehouse → BI/Dashboard**
- ETL = **Extract, Transform, Load** — ดึง แปลง โหลดข้อมูลให้พร้อมวิเคราะห์

**หมายเหตุการออกแบบ:** วาดเป็น flow แนวนอน 4 กล่อง เชื่อมกับ diagram สถาปัตยกรรมจริงที่จะโชว์ในบทที่ 3

## สไลด์ 10 — AWS Core Services ที่ใช้ในระบบ

**เนื้อหา (หัวข้อ 2.1.1-2.1.8 ของบทที่ 2 — บริการสาย pipeline หลัก):**
- **Amazon S3** — Object Storage, Data Lake
- **AWS Lambda** — Serverless, ทำงานอัตโนมัติเมื่อมี Event
- **AWS Glue DataBrew** — ทำความสะอาดข้อมูลแบบ Visual ไม่ต้องเขียนโค้ด
- **AWS Glue ETL Job** — แปลงข้อมูล/สร้าง Star Schema ด้วย Python/Spark
- **AWS Glue Data Catalog** — เก็บ Metadata
- **Amazon Athena** — สืบค้น SQL แบบ Serverless บน S3 (Pay per Query)
- **Amazon Redshift** — คลังข้อมูล Columnar + MPP ประมวลผลเร็ว
- **Amazon EC2** — Virtual Machine โฮสต์เว็บแอป

**หมายเหตุการออกแบบ:** ใช้โลโก้ AWS จริงจากรายงาน (รูปที่ 2.2-2.9) แทนข้อความยาว จะดูเป็นทางการกว่า

## สไลด์ 11 — AWS Supporting Services

**เนื้อหา (หัวข้อ 2.1.9-2.1.12 ของบทที่ 2):**
- **Amazon CloudWatch** — ติดตาม Metrics/Logs/Alarms
- **AWS CloudTrail** — บันทึกกิจกรรมการใช้งานบัญชี AWS เพื่อ Audit
- **AWS IAM** — จัดการตัวตน/สิทธิ์การเข้าถึง
- **Amazon SNS** — ส่งข้อความแจ้งเตือน (Email/SMS/เชื่อมบริการอื่น)

**หมายเหตุการออกแบบ:** จับคู่กับกล่อง "Supporting Services" ในไดอะแกรม Lucid ได้พอดี

## สไลด์ 12 — เทคโนโลยีอื่นที่ใช้พัฒนา

**เนื้อหา (หัวข้อ "เทคโนโลยีที่ใช้" ของบทที่ 2):**
- **Node.js** — JavaScript Runtime ฝั่งเซิร์ฟเวอร์ (Event-Driven, Non-Blocking I/O)
- **Next.js** — Framework บน React (SSR/SSG, จัดการ Routing อัตโนมัติ)
- **SQL** — ภาษาสืบค้น/จัดการข้อมูล ใช้กับ Athena และ Redshift
- **GitHub** — จัดการซอร์สโค้ด/เวอร์ชัน ทำงานร่วมกันเป็นทีม

**หมายเหตุการออกแบบ:** สไลด์ปิดท้ายบทที่ 2 ก่อนเข้าสู่บทที่ 3 (การนำเทคโนโลยีเหล่านี้มาใช้จริง)

# ส่วนที่ 3 — บทที่ 3: ขั้นตอนการดำเนินงาน (9 สไลด์)

## สไลด์ 13 — ความต้องการของระบบ

**เนื้อหา (3.1, 5 ข้อ):**
1. **นำเข้า+อัตโนมัติ** — ตรวจจับไฟล์ใหม่ใน S3 Raw Zone สั่งรัน ETL เองโดยไม่ต้องมีคนกด
2. **ทำความสะอาด+แปลงข้อมูล** — จัดการ Missing Value และแปลงเป็น Star Schema
3. **จัดเก็บข้อมูล** — S3 Curated Zone + Amazon Redshift
4. **แสดงผล+สืบค้น** — Athena + Redshift เปรียบเทียบ พร้อมเว็บ Dashboard
5. **ข้อจำกัด** — ต้องทำงานได้ภายใต้ AWS Academy Learner Lab

**หมายเหตุการออกแบบ:** เป็นสไลด์เปิดบทที่ 3 เชื่อมโยงกลับไปที่ฟังก์ชันหลักในบทที่ 1

## สไลด์ 14 — การออกแบบสถาปัตยกรรมคลาวด์ (Cloud Architecture)

**เนื้อหา (3.2 ข้อ 1, รูปที่ 3.1):**
- Flow: **Database → S3 Raw Zone → Lambda (trigger) → Glue DataBrew (clean) → Glue ETL Job (Star Schema) → S3 Curated Zone → Athena / Redshift → EC2 Dashboard**
- Supporting: CloudWatch, CloudTrail, IAM, SNS ทำงานคลุมทั้งระบบ

**หมายเหตุการออกแบบ:** **สไลด์นี้ใช้ไดอะแกรมที่ทำใน Lucid ได้เต็มหน้าเลย** — เป็นสไลด์สำคัญที่สุดของบทที่ 3 เพราะสรุปทั้งระบบในภาพเดียว

## สไลด์ 15 — การออกแบบโครงสร้างข้อมูล (Star Schema)

**เนื้อหา (3.2 ข้อ 2, รูปที่ 3.2):**
- แสดงตาราง **Fact Table** (คำสั่งซื้อ/ยอดขาย) เชื่อมกับ **Dimension Table** ต่าง ๆ (ลูกค้า/สินค้า/เวลา/ผู้ขาย ฯลฯ)
- อธิบายสั้น ๆ ว่าทำไมต้องใช้ Star Schema — เหมาะกับ query วิเคราะห์ เร็วกว่าโครงสร้างแบบ transactional

**หมายเหตุการออกแบบ:** ใส่รูปที่ 3.2 จากรายงานเต็มหน้า พร้อมวงกลม/ลูกศรชี้ Fact Table ตรงกลาง

## สไลด์ 17 — Use Case: ประมวลผลข้อมูลอัตโนมัติ (UC-01)

**เนื้อหา (ตารางที่ 3.1 สรุปย่อ ไม่ใส่ทุกขั้นตอน):**
- ผู้ดูแลระบบอัปโหลดข้อมูลเข้า S3 → ระบบตรวจจับผ่าน S3 Event → Lambda สั่ง Glue ทำงาน → DataBrew ทำความสะอาด → ETL Job แปลง Star Schema → จัดเก็บ S3 Curated + Redshift → อัปเดต Data Catalog
- Exception: งานชนกัน/ข้อมูลผิดรูปแบบ → บันทึก Log ผ่าน **CloudWatch** + แจ้งเตือนผ่าน **SNS**

**หมายเหตุการออกแบบ:** วาดเป็น flow ลูกศรแนวนอน ไม่ต้องใช้ตาราง 2 คอลัมน์แบบในรายงาน (ยาวเกินไปสำหรับสไลด์)

## สไลด์ 18 — Use Case: ตรวจสอบสถานะ + สืบค้นเปรียบเทียบ (UC-02, UC-03)

**เนื้อหา (ตารางที่ 3.2-3.3 สรุปคู่กัน):**
- **UC-02 ตรวจสอบสถานะ:** ผู้ดูแลระบบเข้า CloudWatch ดู Log ของ Glue/Lambda + ตรวจสอบ CloudTrail เพื่อความปลอดภัย
- **UC-03 สืบค้นเปรียบเทียบ:** รัน SQL เดียวกันผ่าน Athena และ Redshift → เทียบเวลา/ปริมาณข้อมูลที่สแกน/ค่าใช้จ่าย

**หมายเหตุการออกแบบ:** แบ่ง 2 คอลัมน์ซ้าย-ขวา เพื่อรวบ 2 use case ในสไลด์เดียว

## สไลด์ 19 — Use Case: แสดงผลผ่าน Dashboard (UC-04)
