# Use Case Diagram และ Use Case Description (ฉบับแก้ไข) — ระบบ Olytics

> เอกสารนี้สรุปการแก้ไข Use Case Diagram เดิม พร้อมเหตุผลประกอบ และ Use Case Description ฉบับเต็มสำหรับนำไปใช้ในบทที่ 3 ของรายงาน

---

## 1. สรุปสิ่งที่แก้ไขจากฉบับเดิม และเหตุผล

| ปัญหาในฉบับเดิม | เหตุผลที่ต้องแก้ | วิธีแก้ |
|---|---|---|
| ใช้ "Service AWS" เป็น Actor | Actor ต้องเป็นสิ่งที่อยู่ **นอกขอบเขตระบบ** แล้วมาโต้ตอบกับระบบ แต่ S3/Glue/Redshift คือส่วนประกอบของตัวระบบเอง ไม่ใช่สิ่งภายนอก การเอา service มาเป็น Actor เท่ากับบอกว่าระบบเป็น Actor ของตัวเอง ซึ่งผิดหลัก UML | ใช้ Actor ที่เป็นคนหรือระบบภายนอกจริง คือ **ผู้ดูแลระบบ** และ **ผู้ใช้งาน** |
| UC-01 ถึง UC-05 แยกเป็น 5 use case ตามขั้นตอนภายใน | เป็น *functional decomposition* — เอาขั้นตอนทำงานภายในระบบมาวาดเป็น use case ทีละสเต็ป แต่หลักคือ use case ต้องเป็นหน่วยที่ Actor เริ่มแล้วได้ผลลัพธ์ที่มีคุณค่า *จบในตัวเอง* ขั้นตอนย่อยเช่น "ทำความสะอาดข้อมูล" อย่างเดียวไม่จบในตัวเอง ต้องแปลงและจัดเก็บต่อถึงจะมีประโยชน์จริง | รวมเป็น use case เดียวคือ **ประมวลผลข้อมูลอัตโนมัติ** ส่วนราย 5 ขั้นตอนเดิมย้ายไปอยู่ใน Normal Flow ของตาราง Use Case Description แทน |
| UC-06 (สืบค้นเปรียบเทียบ Athena vs Redshift) หายไปจากรูปวาด | เป็นหนึ่งในวัตถุประสงค์หลักของโครงงาน (บทที่ 1 ข้อ 5) แต่ไม่ปรากฏใน diagram ฉบับร่างก่อนหน้า | ใส่กลับเป็น use case แยก |
| ร่างก่อนหน้านี้ (ฉบับที่แล้ว) ยังมี "นำเข้าข้อมูลดิบ" แยกจาก "ประมวลผลข้อมูลอัตโนมัติ" | ขัดกับหลักการรวม use case ที่อธิบายไว้ข้างต้นเอง — ถ้ายึดตามหลักว่า "นำเข้าข้อมูลอย่างเดียวไม่จบในตัวเอง" ก็ต้องไม่มี use case แยกสำหรับมัน เป็นความไม่สอดคล้องที่ต้องแก้ในรอบนี้ | รวมเข้ากับ "ประมวลผลข้อมูลอัตโนมัติ" ให้เหลือ use case เดียวจริงตามหลักที่วางไว้ |

**ผลลัพธ์สุดท้าย: 2 Actor หลัก + 4 Use Case** (ลดจาก 8 use case / 4 actor ในฉบับตัวอย่างของรุ่นพี่ — ไม่ต้องพยายามทำให้เท่ากัน เพราะระบบคนละประเภท: batch pipeline vs transactional web app)

## 2. รายชื่อ Actor

| Actor | ประเภท | บทบาทในระบบ |
|---|---|---|
| ผู้ดูแลระบบ (System Administrator / Data Engineer) | Primary Actor | นำเข้าข้อมูล ตรวจสอบสถานะการทำงานของ Pipeline แก้ไขข้อผิดพลาด |

## 5. Use Case Description (ฉบับเต็ม)

### UC-01: ประมวลผลข้อมูลอัตโนมัติ (Automated Data Processing)

| Use Case Name | ประมวลผลข้อมูลอัตโนมัติ | ID | UC-01 |
|---|---|---|---|
| **Actor** | ผู้ดูแลระบบ (Primary) | | |
| **Stakeholders and Interests** | ผู้ดูแลระบบ ต้องการให้ข้อมูลถูกนำเข้าและประมวลผลถูกต้องโดยไม่ต้องสั่งงานด้วยมือทุกครั้ง / ผู้ใช้งาน ต้องการให้ข้อมูลในคลังข้อมูลเป็นปัจจุบันและถูกต้องอยู่เสมอ | | |
| **Brief Description** | Use case นี้ครอบคลุมกระบวนการนำเข้าข้อมูลดิบ ตรวจจับไฟล์ใหม่ ทำความสะอาดข้อมูล แปลงข้อมูลให้อยู่ในรูปแบบ Star Schema และจัดเก็บลงคลังข้อมูล โดยกระบวนการทั้งหมดทำงานต่อเนื่องกันโดยอัตโนมัติเมื่อมีข้อมูลชุดใหม่เข้าสู่ระบบ | | |

**Normal Flow of ประมวลผลข้อมูลอัตโนมัติ**

| ผู้ดูแลระบบ | ระบบ |
|---|---|
| 1. ผู้ดูแลระบบดึงข้อมูลจากฐานข้อมูลต้นทาง (Database) แบ่งออกเป็นชุด (batch) แล้วอัปโหลดเข้าสู่ S3 Raw Zone | |
| | 2. ระบบตรวจพบไฟล์ใหม่ผ่าน S3 Event Notification และส่ง Event ไปยัง Lambda |
| | 3. Lambda เรียก Glue Job ให้เริ่มทำงาน |
| | 4. Glue DataBrew ทำความสะอาดข้อมูล ลบข้อมูลซ้ำ และจัดการค่าว่าง |
| | 5. Glue ETL Job แปลงข้อมูลให้อยู่ในรูปแบบ Star Schema พร้อมคำนวณค่าที่จำเป็น เช่น ระยะเวลาจัดส่ง |
| | 6. ระบบจัดเก็บผลลัพธ์ไว้ใน S3 Curated Zone และโหลดเข้า Amazon Redshift |
| | 7. Glue Crawler อัปเดต Glue Data Catalog |
| | 8. ระบบบันทึกสถานะการทำงานว่าเสร็จสิ้น |

**Alternate/Exceptional Flows**

- **3-a:** Glue Job มีงานอื่นกำลังทำงานอยู่ (Concurrency เต็ม)
  - 3-a-1: ระบบบันทึก Log ข้อผิดพลาดผ่าน Amazon CloudWatch และส่งการแจ้งเตือนไปยังผู้ดูแลระบบผ่าน Amazon SNS
- **5-a:** ข้อมูลมีรูปแบบผิดพลาดจนไม่สามารถแปลงได้
  - 5-a-1: ระบบบันทึก Error Log ผ่าน Amazon CloudWatch และแจ้งเตือนผู้ดูแลระบบผ่าน Amazon SNS แล้วหยุดกระบวนการเฉพาะไฟล์นั้น
  - 5-a-2: ผู้ดูแลระบบตรวจสอบ Log และแก้ไขข้อมูลต้นทางก่อนนำเข้าใหม่

### UC-02: ตรวจสอบสถานะการทำงาน (Monitor Pipeline Status)

| Use Case Name | ตรวจสอบสถานะการทำงาน | ID | UC-02 |
|---|---|---|---|
| **Actor** | ผู้ดูแลระบบ | | |
| **Stakeholders and Interests** | ผู้ดูแลระบบ ต้องการทราบว่า Pipeline ทำงานสำเร็จหรือมีข้อผิดพลาดเกิดขึ้นที่จุดใด เพื่อแก้ไขได้ทันเวลา | | |
| **Brief Description** | Use case นี้เป็นการตรวจสอบสถานะและ Log การทำงานของ ETL Pipeline ผ่าน Amazon CloudWatch เพื่อยืนยันความถูกต้องของการทำงาน หรือค้นหาสาเหตุเมื่อเกิดข้อผิดพลาด นอกจากนี้ยังสามารถตรวจสอบกิจกรรมการเรียกใช้ AWS API ย้อนหลังผ่าน AWS CloudTrail เพื่อวัตถุประสงค์ด้านความปลอดภัยเพิ่มเติม | | |

**Normal Flow of ตรวจสอบสถานะการทำงาน**

| ผู้ดูแลระบบ | ระบบ |
|---|---|
| 1. ผู้ดูแลระบบเข้าสู่ Amazon CloudWatch Console | |
| | 2. ระบบแสดงรายการ Log ของ Glue Job และ Lambda ที่ทำงานผ่านมา |
| 3. ผู้ดูแลระบบเลือกดูรายละเอียด Log ของงานที่ต้องการตรวจสอบ | |
| | 4. ระบบแสดงสถานะการทำงาน (สำเร็จ / ล้มเหลว) และรายละเอียดข้อผิดพลาด (ถ้ามี) |

**Alternate/Exceptional Flows**

- **4-a:** พบข้อผิดพลาดใน Log
  - 4-a-1: ผู้ดูแลระบบตรวจสอบสาเหตุจากรายละเอียด Error
  - 4-a-2: ผู้ดูแลระบบแก้ไขต้นเหตุ แล้วสั่งรัน Glue Job นั้นใหม่ด้วยตนเองผ่าน AWS Console

### UC-03: สืบค้นและเปรียบเทียบประสิทธิภาพ (Query and Compare Performance)

| Use Case Name | สืบค้นและเปรียบเทียบประสิทธิภาพ | ID | UC-03 |
|---|---|---|---|
| **Actor** | ผู้ใช้งาน / นักวิเคราะห์ข้อมูล | | |
| **Stakeholders and Interests** | ผู้ใช้งาน ต้องการเข้าใจความแตกต่างของการสืบค้นข้อมูลระหว่าง Amazon Athena และ Amazon Redshift ทั้งด้านเวลาและค่าใช้จ่าย เพื่อประกอบการเลือกใช้บริการให้เหมาะกับปริมาณงานจริง | | |
| **Brief Description** | Use case นี้เป็นการสืบค้นข้อมูลชุดเดียวกันผ่าน Amazon Athena (สืบค้นจาก S3 โดยตรงแบบ Serverless) และ Amazon Redshift (สืบค้นจากคลังข้อมูล) เพื่อเปรียบเทียบผลลัพธ์ทั้งด้านเวลาในการประมวลผลและรูปแบบค่าใช้จ่าย | | |

**Normal Flow of สืบค้นและเปรียบเทียบประสิทธิภาพ**

| ผู้ใช้งาน | ระบบ |
|---|---|
| 1. ผู้ใช้งานเขียนคำสั่ง SQL สำหรับสืบค้นข้อมูลที่ต้องการวิเคราะห์ | |
| 2. ผู้ใช้งานรันคำสั่งผ่าน Amazon Athena | |
| | 3. ระบบสืบค้นข้อมูลจาก S3 Curated Zone โดยตรง และแสดงเวลาที่ใช้พร้อมปริมาณข้อมูลที่สแกน |
| 4. ผู้ใช้งานรันคำสั่ง SQL เดียวกันผ่าน Amazon Redshift | |
| | 5. ระบบสืบค้นข้อมูลจากคลังข้อมูล และแสดงเวลาที่ใช้ในการประมวลผล |
| 6. ผู้ใช้งานเปรียบเทียบผลลัพธ์ทั้งสองด้านเวลาและค่าใช้จ่าย | |

**Alternate/Exceptional Flows**

- **3-a:** Athena แจ้งเตือนปริมาณข้อมูลที่ต้องสแกนเกินกว่าที่เหมาะสม
  - 3-a-1: ผู้ใช้งานปรับคำสั่ง SQL ให้จำกัดขอบเขตข้อมูล (เช่น ระบุช่วงเวลา) แล้วสืบค้นใหม่

### UC-04: แสดงผลการวิเคราะห์ผ่าน Dashboard (View Analytics Dashboard)

| Use Case Name | แสดงผลการวิเคราะห์ผ่าน Dashboard | ID | UC-04 |
|---|---|---|---|
| **Actor** | ผู้ใช้งาน | | |
| **Stakeholders and Interests** | ผู้ใช้งาน ต้องการเข้าใจข้อมูลเชิงธุรกิจในรูปแบบที่เข้าใจง่ายและนำไปใช้ประกอบการตัดสินใจได้ | | |
| **Brief Description** | Use case นี้เป็นการเข้าดูผลการวิเคราะห์ข้อมูลเชิงธุรกิจผ่านเว็บแอปพลิเคชัน Dashboard ที่พัฒนาขึ้นด้วย Next.js โดยดึงข้อมูลจาก Amazon Redshift | | |

**Normal Flow of แสดงผลการวิเคราะห์ผ่าน Dashboard**

| ผู้ใช้งาน | ระบบ |
|---|---|
| 1. ผู้ใช้งานเข้าสู่เว็บแอปพลิเคชัน Dashboard ผ่านเบราว์เซอร์ | |
| | 2. เว็บแอปพลิเคชันร้องขอข้อมูลจาก Amazon Redshift ผ่าน API ที่พัฒนาขึ้น |
| | 3. ระบบแสดงผลข้อมูลในรูปแบบกราฟและตาราง เช่น แนวโน้มยอดขายรายเดือน หมวดสินค้ายอดนิยม และความสัมพันธ์ระหว่างระยะเวลาจัดส่งกับคะแนนรีวิว |
| 4. ผู้ใช้งานเลือกกรองข้อมูลตามช่วงเวลาหรือหมวดหมู่ที่ต้องการ | |
| | 5. ระบบแสดงผลข้อมูลที่กรองแล้ว |

**Alternate/Exceptional Flows**

- **2-a:** ไม่สามารถเชื่อมต่อกับ Amazon Redshift ได้
  - 2-a-1: ระบบแสดงข้อความแจ้งเตือนข้อผิดพลาดให้ผู้ใช้งานทราบ
