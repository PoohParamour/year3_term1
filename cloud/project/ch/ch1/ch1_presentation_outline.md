## สไลด์ 2 — ที่มาของปัญหา (1/2)

**หัวข้อสไลด์:** ความเป็นมาและปัญหา

**เนื้อหา (สรุปจาก 1.1 ย่อหน้า 1-2):**
- ธุรกิจ E-Commerce เติบโตเร็ว → ข้อมูลมหาศาลทุกวัน (คำสั่งซื้อ สินค้า ลูกค้า ผู้ขาย การชำระเงิน รีวิว)
- ข้อมูลกระจัดกระจายในหลายตาราง/ระบบ ที่ออกแบบมาเพื่อ **Transactional System** ไม่ใช่การวิเคราะห์
- การเชื่อมโยงข้อมูลจำนวนมากทำได้ช้า และกระทบประสิทธิภาพระบบหลัก

**หมายเหตุการออกแบบ:** ใช้ไอคอนประกอบ (คำสั่งซื้อ/สินค้า/ลูกค้า/ผู้ขาย) แทนข้อความยาว

## สไลด์ 3 — ที่มาของปัญหา (2/2)

**หัวข้อสไลด์:** ทำไมต้อง Data Warehouse บนคลาวด์

**เนื้อหา (สรุปจาก 1.1 ย่อหน้า 3-4):**
- แนวคิด **Data Warehouse** = แยกพื้นที่วิเคราะห์ออกจากระบบงานหลัก
- Data Warehouse แบบ on-premise → ลงทุนฮาร์ดแวร์สูง + ดูแลต่อเนื่อง (ข้อจำกัดสำหรับองค์กรเล็ก/ผู้เริ่มต้น)
- ข้อมูลจริงเข้ามาต่อเนื่องตามรอบธุรกิจ → ระบบต้องรองรับการนำเข้าอัตโนมัติ ลดงานมือ ลดความผิดพลาด

**หมายเหตุการออกแบบ:** เปรียบเทียบ on-prem vs cloud แบบ 2 คอลัมน์สั้น ๆ ได้

---

## สไลด์ 4 — แนวคิดโครงงาน

**หัวข้อสไลด์:** แนวคิดโครงงาน (1.1 ย่อหน้าสุดท้าย)

**เนื้อหา:**
- พัฒนาระบบคลังข้อมูลบน **Amazon Web Services (AWS)**
- ใช้ข้อมูลจริงจาก **Olist** (อีคอมเมิร์ซ บราซิล) กว่า **100,000 คำสั่งซื้อ** ปี 2016–2018
- นำเข้า → แปลง → จัดเก็บแบบ **Star Schema** พร้อมทำงานอัตโนมัติเมื่อมีข้อมูลใหม่
- แสดงให้เห็นว่าไม่ต้องลงทุนฮาร์ดแวร์จริง ปรับขยายได้ตามต้องการ จ่ายตามการใช้งานจริง

**หมายเหตุการออกแบบ:** สไลด์นี้เหมาะเป็นจุดเปลี่ยนผ่านไปสู่วัตถุประสงค์ ใส่โลโก้ AWS + โลโก้/ไอคอน Olist ได้

## สไลด์ 5 — วัตถุประสงค์ของโครงงาน

**หัวข้อสไลด์:** วัตถุประสงค์ (1.2)

**เนื้อหา (6 ข้อ ย่อให้สั้นลง):**
1. ศึกษา/ออกแบบสถาปัตยกรรม Data Warehouse บนคลาวด์ (AWS)
2. พัฒนา ETL แปลงข้อมูลให้เป็น Star Schema
3. ศึกษาการทำงานของ ETL Pipeline แบบอัตโนมัติ
4. แสดงว่าจัดเก็บ/ประมวลผลข้อมูลใหญ่ได้โดยไม่ต้องมีฮาร์ดแวร์จริง
5. เปรียบเทียบ Amazon Athena vs Amazon Redshift (ประสิทธิภาพ/ค่าใช้จ่าย)
6. นำเสนอผลวิเคราะห์เชิงธุรกิจผ่าน Dashboard

**หมายเหตุการออกแบบ:** ใช้ numbered list สั้น ๆ 6 ข้อพอดีหน้าเดียว ไม่ต้องมีคำอธิบายเพิ่ม

## สไลด์ 6 — ขอบเขตของระบบ: ภาพรวม

**หัวข้อสไลด์:** ขอบเขตของระบบ (1.3.1)

**เนื้อหา:**
- นำเทคโนโลยีคลาวด์มาจัดการวงจรข้อมูลอีคอมเมิร์ซครบวงจร:
  **นำเข้าข้อมูลดิบ → ทำความสะอาด → แปลงข้อมูล → จัดเก็บคลังข้อมูล → แสดงผลวิเคราะห์**
- เน้น 3 เรื่อง: ความถูกต้องของข้อมูล / การทำงานอัตโนมัติ / ความคุ้มค่าใต้ข้อจำกัดงบประมาณ

**หมายเหตุการออกแบบ:** เหมาะใส่ไดอะแกรม flow แนวนอนสั้น ๆ (5 กล่อง) เกริ่นก่อนลงรายละเอียดสไลด์ถัดไป

## สไลด์ 7 — ฟังก์ชันหลักของระบบ

**หัวข้อสไลด์:** ฟังก์ชันหลัก (1.3.2)

**เนื้อหา (7 ระบบย่อย ย่อเหลือชื่อ+หน้าที่สั้น):**
1. นำเข้าข้อมูลดิบ — จาก Database → แบ่ง batch → S3 Raw Zone
2. ตรวจจับข้อมูลใหม่ + สั่งงานอัตโนมัติ — ไม่ต้องสั่งด้วยมือ
3. ทำความสะอาดข้อมูล — ลบซ้ำ/ค่าว่าง/รูปแบบผิด
4. แปลงข้อมูลสู่ Star Schema — Fact + Dimension Table
5. จัดเก็บคลังข้อมูล — S3 Curated Zone + Redshift
6. สืบค้น/เปรียบเทียบประสิทธิภาพ — Athena vs Redshift
7. แสดงผลการวิเคราะห์ — Dashboard บนเว็บแอป

**หมายเหตุการออกแบบ:** **สไลด์นี้ใช้ไดอะแกรมสถาปัตยกรรมที่ทำไว้ใน Lucid ประกอบได้เลย** (S3→Lambda→DataBrew→Glue ETL→S3→Athena/Redshift→EC2) จะช่วยให้เห็นภาพ flow ชัดกว่าอ่านข้อความ 7 ข้อ

## สไลด์ 8 — บริการ AWS หลัก (Core Pipeline)

**หัวข้อสไลด์:** เทคโนโลยีที่ใช้ — AWS Core Services (1.3.3 ส่วนที่ 1)

**เนื้อหา (จากตาราง 1.1 เฉพาะ pipeline หลัก):**
| บริการ | หน้าที่ |
|---|---|
| Amazon S3 | Data Lake (Raw + Curated Zone) |
| AWS Glue DataBrew | ทำความสะอาดข้อมูล |
| AWS Glue ETL Job | แปลงเป็น Star Schema |
| AWS Glue Data Catalog | เก็บ Metadata/Schema |
| Amazon Redshift | คลังข้อมูล (Fact/Dimension) |
| Amazon Athena | สืบค้นตรงจาก S3 |
| AWS Lambda | trigger อัตโนมัติเมื่อมีไฟล์ใหม่ |
| Amazon EC2 | โฮสต์เว็บแอป Dashboard |

**หมายเหตุการออกแบบ:** ใช้ไอคอน AWS จริงแทนตาราง จะดูมืออาชีพกว่า (ใช้ชุดไอคอนเดียวกับ diagram ที่ทำใน Lucid)

## สไลด์ 9 — บริการสนับสนุน + เทคโนโลยีอื่น

**หัวข้อสไลด์:** เทคโนโลยีที่ใช้ — Supporting Services & อื่น ๆ (1.3.3 ส่วนที่ 2)

**เนื้อหา:**
- **Amazon CloudWatch** — ติดตามการทำงาน/Log ของ ETL Job
- **AWS CloudTrail** — บันทึกการเรียกใช้ API เพื่อความปลอดภัย
- **AWS IAM (LabRole)** — กำหนดสิทธิ์การเข้าถึงระหว่างบริการ
- **Amazon SNS** — แจ้งเตือนสถานะ Pipeline (สำเร็จ/ล้มเหลว)

เทคโนโลยีนอกเหนือ AWS:
- Python (สคริปต์ ETL/อัตโนมัติ), SQL (คลังข้อมูล/สืบค้น), Next.js + Node.js (เว็บ Dashboard), GitHub (version control)

**หมายเหตุการออกแบบ:** จับคู่กับกล่อง "Supporting Services" ในไดอะแกรม Lucid ได้พอดี (CloudWatch, CloudTrail, IAM, SNS)

## สไลด์ 10 — ข้อจำกัดของระบบ

**หัวข้อสไลด์:** ข้อจำกัดของระบบ (1.3.4)

**เนื้อหา (จัดกลุ่ม 9 ข้อให้เหลือ 4 กลุ่มเพื่ออ่านง่าย):**
- **Region/บริการ:** ใช้ได้เฉพาะ us-east-1, us-west-2
- **ขนาด/จำนวน resource:** Glue (Worker ≤10, Concurrency 1), Redshift (ra3.large, ≤2 instance), Lambda (≤10 concurrent), EC2 (nano–large, ≤9 instance, ≤32 vCPU)
- **สิทธิ์/บริการที่ใช้ไม่ได้:** สร้าง IAM User/Role ใหม่ไม่ได้ (ใช้ LabRole เท่านั้น), ใช้ QuickSight ไม่ได้ → ต้องสร้างเว็บ Dashboard เอง
- **ขอบเขตงาน:** งบประมาณจำกัด (เกินงบ = บัญชีถูกปิด), เน้น Batch ไม่ใช่ Real-time, ข้อมูล ~100,000 รายการ (ผลเทียบ Athena/Redshift อาจไม่ต่างมาก)

**หมายเหตุการออกแบบ:** จัดเป็น 4 กล่องใน 1 สไลด์ (2x2 grid) แทนการไล่ bullet 9 ข้อยาว ๆ

## สไลด์ 11 — ความปลอดภัย และข้อกำหนดการใช้งาน

**หัวข้อสไลด์:** ความปลอดภัย & การใช้งานระบบ (1.3.5 + 1.3.6)

**เนื้อหา:**

ความปลอดภัย:
- เข้ารหัสข้อมูลบน S3 (Server-Side Encryption)
- จำกัด Security Group ของ Redshift/EC2 เฉพาะที่จำเป็น
- สิทธิ์เข้าถึงผ่าน LabRole เท่านั้น
- บันทึก API calls ผ่าน CloudTrail
- ข้อมูลต้นทางถูกปกปิดตัวตนแล้ว (ไม่มี PII)

การใช้งาน:
- จัดการผ่าน AWS Console / CLI ภายในเซสชัน Learner Lab
- Credentials เปลี่ยนใหม่ทุกเซสชัน ต้องตั้งค่าใหม่ทุกครั้ง
- ผู้ใช้เข้าถึงผลวิเคราะห์ผ่าน Dashboard โดยไม่ต้องแตะคลังข้อมูลตรง
- ปิด resource ที่มีค่าใช้จ่ายต่อเนื่อง (Redshift/EC2) เมื่อไม่ใช้งาน

**หมายเหตุการออกแบบ:** แบ่ง 2 คอลัมน์ซ้าย-ขวา (ความปลอดภัย | การใช้งาน) ในสไลด์เดียว

## สไลด์ 12 — ประโยชน์ที่คาดว่าจะได้รับ

**หัวข้อสไลด์:** ประโยชน์ที่คาดว่าจะได้รับ (1.4)

**เนื้อหา (จัดกลุ่ม 8 ข้อเป็น 3 ธีม):**

**ด้านเทคนิค**
- ได้ระบบคลังข้อมูลรองรับ 100,000+ รายการอย่างมีประสิทธิภาพ
- เข้าใจหลักออกแบบ Star Schema (Fact/Dimension Table)
- เข้าใจ ETL Pipeline บนคลาวด์ตั้งแต่ต้นจนจบ
- เข้าใจการออกแบบระบบอัตโนมัติเมื่อมีข้อมูลใหม่

**ด้านธุรกิจ/การตัดสินใจ**
- ได้ insight เชิงธุรกิจ (แนวโน้มยอดขาย, สินค้ายอดนิยม, ความสัมพันธ์เวลาจัดส่ง-รีวิว)
- เข้าใจความต่าง Serverless (Athena) vs คลังข้อมูลเฉพาะทาง (Redshift) ทั้งประสิทธิภาพ/ค่าใช้จ่าย
- ประเมินค่าใช้จ่ายและเลือกบริการคลาวด์ให้เหมาะกับงานได้

**ด้านทีม**
- ประสบการณ์วางแผน ติดตามงาน แก้ปัญหาร่วมกันเป็นทีม

**หมายเหตุการออกแบบ:** ใช้ 3 คอลัมน์ (เทคนิค / ธุรกิจ / ทีม) แทนการไล่เลข 1-8 ยาว ๆ ปิดท้ายบทที่ 1 ได้พอดี
