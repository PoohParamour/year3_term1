> "ผมใช้ชุดข้อมูลลูกค้าบัตรเครดิต 10,127 คน แก้โจทย์ธุรกิจ 2 เคสด้วย Decision Tree
> เคสแรกทำนายลูกค้าที่จะเลิกใช้บัตร เคสที่สองคัดลูกค้าบัตร Blue ที่โปรไฟล์เหมือนลูกค้าพรีเมียมเพื่อส่งแคมเปญอัปเกรด

## 2. ทำความเข้าใจข้อมูลก่อน (ตัวเลขที่ต้องจำได้)

| สิ่งที่ต้องจำ | ตัวเลข | ความหมาย |
|--------------|--------|----------|
| ขนาดข้อมูล | 10,127 แถว × 21 คอลัมน์ | |
| Missing value | **0** | ไม่ต้อง impute |
| Attrited (จะเลิกใช้) | 1,627 คน = **16.1%** | ข้อมูลไม่สมดุล |
| Blue / Silver / Gold / Platinum | 9,436 / 555 / 116 / **20** | Platinum น้อยมาก |
| `Unknown` ใน Education / Income / Marital | 1,519 / 1,112 / 749 | เก็บเป็นหมวดหนึ่ง ไม่เติมค่า |

### ❓ "ทำไมทิ้ง `CLIENTNUM`?"
เพราะไม่ซ้ำเลยสักแถว (10,127 ค่าจาก 10,127 แถว) = เป็นแค่รหัสประจำตัว ไม่มีข้อมูลพฤติกรรม
ถ้าปล่อยไว้ Decision Tree อาจใช้มันแตกกิ่งจนจำข้อมูลได้ทั้งชุด = overfit ทันที

### ❓ "ทำไมไม่เติมค่า Unknown?"
เพราะ `Unknown` ในที่นี้ **ไม่ใช่ข้อมูลหาย แต่คือ "ลูกค้าไม่ยอมให้ข้อมูล"** ซึ่งตัวมันเองอาจเป็นสัญญาณเชิงพฤติกรรม
ถ้าเราเติมด้วยค่าฐานนิยม เท่ากับทำลายสัญญาณนั้นทิ้ง เราจึงแทนด้วย **-1** เพื่อให้มันอยู่แยกจากค่าจริงทั้งหมด
Decision Tree จะได้แตกกิ่งแยกกลุ่มนี้ออกมาได้เองถ้ามันมีประโยชน์

## 3. ⭐ Data Leakage — หัวใจของงานนี้

### สิ่งที่เจอ
จากพจนานุกรมข้อมูล มีสองสูตรที่น่าสงสัย และผมเอาไปทดสอบกับข้อมูลจริง **ตรงเป๊ะทั้ง 10,127 แถว (100.00%)**:

```
Avg_Open_To_Buy        = Credit_Limit - Total_Revolving_Bal
Avg_Utilization_Ratio  = Total_Revolving_Bal / Credit_Limit
```

แปลว่าสองคอลัมน์นี้ **ไม่ใช่ข้อมูลใหม่** มันคือ `Credit_Limit` กับ `Total_Revolving_Bal` ที่เอามาคำนวณต่อ

### ทำไมมันเป็นปัญหาเฉพาะ Case 2
* Case 2 ทำนาย `Card_Category` แต่ **วงเงินถูกกำหนดตอนอนุมัติบัตร** = มันคือ *ผลลัพธ์* ของการเป็นลูกค้าพรีเมียม ไม่ใช่ *สาเหตุ*
* ในข้อมูล ลูกค้า Premium ที่วงเงินต่ำกว่า 5,000 มีแค่ **2 คน** จาก 691 คน → วงเงินแทบบอกคำตอบได้เลย
* **หลักฐานที่ผมรันให้ดูในโน้ตบุ๊ก:** โมเดลที่ "ลืม" ตัดฟีเจอร์รั่ว ได้ Recall 0.9855 ดูสวยมาก
  แต่พอดู feature importance พบว่า **ทุ่มน้ำหนักไปที่ `Credit_Limit` ถึง 75%** = มันแค่ท่องว่า "วงเงินสูง = พรีเมียม"
  ไม่ได้เรียนพฤติกรรมการใช้จ่ายเลย ซึ่งไม่ตอบโจทย์ที่ธนาคารถามมาสักนิด

### สรุปการตัดสินใจ
| | Case 1 (Churn) | Case 2 (Up-selling) |
|---|---|---|
| `Credit_Limit` | ✅ ใช้ได้ | ❌ ตัดออก |
| `Avg_Open_To_Buy` | ✅ ใช้ได้ | ❌ ตัดออก |
| `Avg_Utilization_Ratio` | ✅ ใช้ได้ | ❌ ตัดออก |

> **ต้องตัดทั้งสามตัวพร้อมกัน** ถ้าตัดแค่ `Credit_Limit` ตัวเดียว ข้อมูลจะรั่วผ่านอีกสองตัวอยู่ดี เพราะมันคำนวณมาจากกันและกัน

### ❓ ถ้า TA ถามว่า "แล้ว Case 1 ทำไมไม่ตัด?"
เพราะ Case 1 ทำนาย `Attrition_Flag` ซึ่ง**ไม่ได้มีความสัมพันธ์เชิงสูตร**กับวงเงิน
ตอนที่ธนาคารจะใช้โมเดลจริง วงเงินของลูกค้าเป็นข้อมูลที่รู้อยู่แล้ว ณ เวลานั้น ไม่ใช่ข้อมูลจากอนาคต → ใช้ได้ตามปกติ
(และผลลัพธ์ก็ยืนยัน: `Credit_Limit` มี importance แค่ 0.0116 = โมเดลแทบไม่สนใจมันอยู่แล้ว)

## 4. Preprocessing — ทำไมแปลงแบบนี้

| คอลัมน์ | วิธี | เหตุผลที่ต้องพูด |
|---------|------|-----------------|
| `Gender` | `map()` → 0/1 | มีแค่ 2 ค่า ทำ One-Hot ไปก็ได้คอลัมน์ซ้ำซ้อน |
| `Education_Level` | **Ordinal** 0–5 | **มีลำดับ** (Uneducated < High School < ... < Doctorate) การเก็บลำดับไว้ทำให้ tree แตกกิ่งแบบ "≤ 2.5" ได้ทีเดียวจบ ถ้า One-Hot ต้องแตกทีละหมวด เปลืองความลึก |
| `Income_Category` | **Ordinal** 0–4 | เหตุผลเดียวกัน มีลำดับชัดเจน |
| `Marital_Status` | **One-Hot** | **ไม่มีลำดับ** — "โสด" ไม่ได้น้อยกว่า "แต่งงาน" ถ้าใส่เป็นตัวเลข 0/1/2 เท่ากับยัดลำดับปลอมเข้าไป |
| `Card_Category` | **Ordinal** 0–3 | มีลำดับ (Blue < Silver < Gold < Platinum) |
| `Unknown` ทุกคอลัมน์ | **-1** | แยกออกจากค่าจริงทั้งหมด |

### ❓ "ทำไมไม่ทำ StandardScaler?"
**Decision Tree ไม่ต้อง scale เลย** เพราะมันตัดสินใจโดยเทียบค่า threshold **ทีละฟีเจอร์** (`Total_Trans_Ct <= 57.5`)
ไม่ได้คำนวณระยะทางข้ามฟีเจอร์ ดังนั้นหน่วยจะเป็นบาทหรือเป็นเดือนก็ไม่กระทบ

แต่ **KNN กับ Logistic Regression ต้อง scale** เพราะ KNN ใช้ระยะทางแบบยุคลิด
ถ้าไม่ scale `Total_Trans_Amt` (หลักหมื่น) จะกลบ `Months_Inactive_12_mon` (หลักหน่วย) จนหมด
ในโน้ตบุ๊กผม `fit` scaler **บนชุด train เท่านั้น** แล้ว `transform` ทั้งสองชุด — ถ้า fit ทั้งก้อนคือปล่อยให้ค่าเฉลี่ยของ test รั่วเข้า train

## 5. Case 1: Churn Prediction

### เป้าหมาย
ทำนาย `Attrition_Flag` (0 = Existing, 1 = Attrited)

### ❓ "ทำไมไม่ใช้ Accuracy ตัดสิน?"
เพราะข้อมูลไม่สมดุล — Attrited มีแค่ 16.1%
**ถ้าโมเดลโง่ ๆ ทายว่า "ทุกคนอยู่ต่อ" จะได้ Accuracy ตั้ง 83.9% ทั้งที่หาลูกค้าเสี่ยงไม่เจอเลยสักคน**
ผมจึงดู **Recall และ F1 ของคลาส Attrited** เป็นหลัก และตัวเลขในตารางทั้งหมดผมคิดจากคลาส 1 เท่านั้น ไม่ใช่ค่าเฉลี่ยถ่วงน้ำหนัก

**เหตุผลเชิงธุรกิจ:** พลาดลูกค้าที่กำลังจะหนี 1 คน = เสียลูกค้าจริง ๆ 1 คน (แพงมาก)
แต่โทรหาคนที่ไม่ได้จะหนี = เสียแค่ค่าโทร → **Recall สำคัญกว่า Precision**

### ❓ "`class_weight='balanced'` ทำอะไร?"
สั่งให้โมเดลถ่วงน้ำหนักคลาสส่วนน้อยมากขึ้นตามสัดส่วนผกผัน
พูดง่าย ๆ คือ "ทายพลาดลูกค้าที่จะหนี ถือว่าผิดหนักกว่าทายพลาดลูกค้าที่อยู่ต่อ"
ผลคือยอมแลก Precision ลงนิดหน่อยเพื่อดัน Recall ขึ้น ซึ่งตรงกับต้นทุนทางธุรกิจข้างบน

### ❓ "หา max_depth ยังไง?"
1. รันต้นไม้แบบไม่จำกัดความลึกก่อน → ได้ **ความลึก 19, 309 ใบ, F1 บน train = 1.0000 แต่ test = 0.8074**
   → นี่คือ **Overfitting** ชัด ๆ (จำข้อมูลฝึกได้หมดแต่ใช้กับข้อมูลใหม่ไม่ได้)
2. ทำ **Pruning** โดยลอง `max_depth` 2–20 แล้ววัดด้วย **5-Fold Cross-Validation บนชุด train**
3. ได้ **max_depth = 12**

> ⭐ **จุดที่ควรเน้นกับ TA:** ผม**ไม่ได้**เลือกความลึกจากคะแนนบนชุด test
> เพราะนั่นเท่ากับแอบดูข้อสอบก่อนสอบ (test leakage) — ชุด test ถูกใช้แค่ครั้งเดียวตอนวัดผลสุดท้าย
> กราฟที่ได้คือภาพ **Bias–Variance Tradeoff** คลาสสิก: เส้น Train ไต่ขึ้นจนแตะ 1.0 แต่เส้น CV ขึ้นถึงจุดหนึ่งแล้วตก

### ผลลัพธ์ Case 1

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| **Decision Tree (depth=12)** | **0.9408** | 0.8042 | **0.8338** | **0.8187** | 0.9023 |
| KNN (k=5) | 0.8963 | 0.8075 | 0.4646 | 0.5898 | 0.9060 |
| Logistic Regression | 0.8524 | 0.5256 | 0.8215 | 0.6411 | **0.9199** |

**วิธีเล่าผล:**
* DT ชนะ F1 ขาด — จับลูกค้าเสี่ยงได้พอ ๆ กับ LogReg (Recall 0.83 vs 0.82) **แต่ Precision สูงกว่าเกือบเท่าตัว** (0.80 vs 0.53)
  แปลว่า **รบกวนลูกค้าที่ไม่ได้จะหนีน้อยกว่ามาก = ต้นทุนแคมเปญถูกกว่า**
* KNN แย่สุด **Recall แค่ 0.46 = พลาดลูกค้าที่กำลังจะหนีไปกว่าครึ่ง** ใช้งานจริงไม่ได้เลย

### ⚠️ ประเด็นที่ต้องพูดเอง อย่ารอให้ TA จับได้
**ROC-AUC ของ Logistic Regression (0.9199) สูงกว่า Decision Tree (0.9023)**

อธิบายว่า: ROC-AUC วัด "คุณภาพการเรียงลำดับด้วยค่าความน่าจะเป็น"
Logistic Regression ให้ค่าความน่าจะเป็นเป็นตัวเลข**ต่อเนื่องละเอียด** ส่วน Decision Tree ให้ค่าเป็น**ขั้น ๆ**
(ทุกคนที่ตกในใบเดียวกันได้คะแนนเท่ากันหมด) กราฟ ROC จึงหยาบกว่าโดยธรรมชาติ
**แต่พอตัดสินใจจริงที่ threshold 0.5 ซึ่งเป็นสิ่งที่ระบบ Retention ใช้งานจริง Decision Tree ทำได้ดีกว่าชัดเจน**

### กฎที่ได้จากต้นไม้ (เอาไปคุยกับฝ่ายธุรกิจได้เลย)
```
|--- Total_Trans_Ct <= 57.5           ← root node: รูดบัตรน้อยกว่า 57.5 ครั้ง/ปี
|   |--- Total_Revolving_Bal <= 656.5 ← ยอดคงค้างใกล้ศูนย์  → กลุ่มเสี่ยงสูง
|   |--- Total_Revolving_Bal >  656.5
|--- Total_Trans_Ct >  57.5           ← รูดบัตรบ่อย → ปลอดภัย
```

**Feature Importance:**
1. `Total_Trans_Ct` (0.44) — จำนวนครั้งที่รูดบัตร (root node ที่เกณฑ์ 57.5 ครั้ง/ปี)
2. `Total_Trans_Amt` (0.18) — ยอดใช้จ่ายรวม
3. `Total_Revolving_Bal` (0.11) — ยอดคงค้างใกล้ 0 = ปิดยอดแล้วเลิกใช้
4. `Total_Ct_Chng_Q4_Q1` (0.08) — ความถี่ใน Q4 ลดลงเทียบ Q1 = กำลังถอยห่าง
5. `Total_Relationship_Count` (0.06) — ถือผลิตภัณฑ์น้อย = ผูกพันน้อย ย้ายง่าย

> **ประโยคปิด Case 1:** "ข้อมูลประชากรศาสตร์อย่างอายุ การศึกษา รายได้ แทบไม่มีน้ำหนักเลย
> สรุปคือ **ลูกค้าจะหนีหรือไม่ ดูจากพฤติกรรมการใช้บัตร ไม่ใช่ดูว่าเขาเป็นใคร**"

## 6. Case 2: Up-selling Lookalike

### ❓ "แปลงโจทย์ธุรกิจเป็นโจทย์ ML ยังไง?" (คำถามที่ TA น่าจะถามที่สุด)

1. สอนโมเดลให้รู้จัก **"หน้าตาของลูกค้าพรีเมียม"** → Binary Classification: Blue (0) vs Premium (1)
2. เอาโมเดลไปให้คะแนน `predict_proba` กับลูกค้า **Blue** ทุกคน
3. ลูกค้า Blue ที่ได้คะแนนสูง = *"ระบบคิดว่าคนนี้คือพรีเมียม แต่ความจริงยังถือ Blue อยู่"* → **นี่คือกลุ่มเป้าหมาย**

> ⭐ **ประโยคที่ทำให้ TA พยักหน้า:**
> "ในเคสนี้ **การที่โมเดลทายผิดไม่ใช่ความผิดพลาด แต่คือคำตอบที่เราต้องการ**"

### ❓ "ทำไมยุบ 4 คลาสเหลือ 2 คลาส?"
เพราะ **Platinum มีแค่ 20 แถว** จาก 10,127 แถว
แบ่ง train/test แล้วเหลือใน test แค่ 4 คน — วัดผลอะไรไม่ได้เลย โมเดลก็เรียนรู้ไม่ทัน
และโจทย์ถามว่า "คัดลูกค้า Blue ที่ใกล้เคียงกลุ่มพรีเมียม" **ไม่ได้ถามว่าต้องอัปเป็นระดับไหน** → Binary จึงตอบโจทย์ครบอยู่แล้ว

### ❓ "ทำไม Case 2 จูนด้วย ROC-AUC แต่ Case 1 จูนด้วย F1?"
| | Case 1 | Case 2 |
|---|---|---|
| ต้องการ | **คำตอบขาด** "คนนี้เสี่ยงไหม" | **ลำดับ** "ควรโทรหาใครก่อน" |
| ใช้ที่ threshold 0.5 | ใช่ | ไม่ใช่ เอาคะแนนไปเรียงอันดับ |
| เมตริก | **F1** | **ROC-AUC** (วัดความสามารถในการเรียงลำดับโดยตรง) |

อีกเหตุผล: **ต้นไม้ตื้นเกินไปให้ค่าความน่าจะเป็นได้แค่ไม่กี่ระดับ** (1 ใบ = 1 ค่า)
ถ้าจูนด้วย F1 จะได้ depth=2 ซึ่งลูกค้าหลายพันคนได้คะแนนเท่ากันหมดจนเรียงอันดับไม่ได้
พอจูนด้วย ROC-AUC ได้ **depth=4** ซึ่งให้คะแนน **13 ระดับ** เรียงอันดับได้จริง

### ผลลัพธ์ Case 2

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| **Decision Tree (depth=4)** | 0.6471 | 0.1199 | **0.6594** | 0.2029 | **0.7229** |
| KNN (k=3) | **0.9215** | 0.2308 | 0.0652 | 0.1017 | 0.6111 |
| Logistic Regression | 0.7192 | 0.1366 | 0.5870 | 0.2216 | 0.6971 |

### ⚠️ ต้องอธิบายตารางนี้ให้ถูก ไม่งั้นดูเหมือนงานพัง

**1. KNN ที่ Accuracy 0.92 คือภาพลวงตา**
ดู Recall ประกอบ — ได้แค่ **0.065** แปลว่า **KNN แทบทายว่า "Blue" ทุกคน**
ซึ่งได้ Accuracy สวยงามอัตโนมัติเพราะ 93% ของข้อมูลคือ Blue แต่หาลูกค้าเป้าหมายไม่เจอเลย
→ นี่คือ **Accuracy Paradox** ในข้อมูลไม่สมดุล

**2. Precision ต่ำ (0.12) ไม่ใช่ปัญหาในเคสนี้**
Precision ต่ำเพราะช่อง "ทายว่า Premium แต่จริง ๆ เป็น Blue" มีเยอะ
**แต่คนกลุ่มนั้นแหละคือผลลัพธ์ที่ธนาคารต้องการ** — ลูกค้า Blue ที่โปรไฟล์เหมือนพรีเมียมจนโมเดลแยกไม่ออก

**3. คะแนนทุกโมเดลต่ำลงทั้งกระดาน = สมเหตุสมผล**
เพราะพอตัดวงเงินออกแล้ว Blue กับ Premium มีพฤติกรรมทับซ้อนกันสูงมาก
พูดอีกอย่างคือ **มีลูกค้า Blue จำนวนไม่น้อยที่ "สมควรได้อัปเกรด" อยู่แล้ว** — ซึ่งก็คือสิ่งที่โจทย์ให้ไปหา
**โมเดลที่ได้คะแนนสูงลิ่วในเคสนี้ต่างหากที่ควรถูกสงสัยว่ามีฟีเจอร์รั่ว**

### ผลลัพธ์ที่ส่งให้ฝ่ายการตลาด
ตาราง Top 15 ลูกค้า Blue พร้อม Upgrade Score + พิสูจน์ว่าโมเดลไม่ได้สุ่มเลือก:

| | ยอดใช้จ่ายเฉลี่ย | จำนวนครั้งที่รูด | ผลิตภัณฑ์ที่ถือ |
|---|---|---|---|
| **กลุ่มเป้าหมาย (Top 10%)** | **11,824** | **100.6** | 2.1 |
| Blue ทั่วไป | 3,361 | 59.7 | 4.0 |

กลุ่มเป้าหมายใช้จ่ายมากกว่า **3.5 เท่า** และรูดบัตรบ่อยกว่าเกือบ 2 เท่า → โมเดลคัดคนที่ "ใช้จ่ายระดับพรีเมียมอยู่แล้วแต่ยังถือบัตร Blue" ได้จริง

### ข้อควรระวังที่ควรพูดเอง (ได้ใจ TA)
1. **`Gender` ติด feature importance อันดับต้น ๆ** — การส่งแคมเปญโดยอิงเพศอาจเข้าข่ายการเลือกปฏิบัติ
   และผิดหลักการให้บริการทางการเงินอย่างเป็นธรรม ในงานจริงควรตัดออกแล้วดูว่า AUC ลดลงมากไหม
2. **ควรกรองลูกค้าที่ `Attrition_Flag = Attrited` ออกก่อนส่งแคมเปญ** — ไม่มีประโยชน์ที่จะเชิญอัปเกรดบัตร
   ให้คนที่เลิกใช้บริการไปแล้ว → **จุดที่โมเดล Case 1 กับ Case 2 ทำงานเสริมกัน**
3. **กลุ่มเป้าหมายถือผลิตภัณฑ์น้อยกว่า (2.1 vs 4.0)** — อ่านได้สองแบบ อาจเป็นโอกาสขายเพิ่ม
   หรืออาจเป็นเพราะกลุ่มพรีเมียมเดิมก็ถือน้อยอยู่แล้ว โมเดลจึงเรียนรู้รูปแบบนี้มา ควรเช็คกับฝ่ายธุรกิจก่อน

## 7. ทำไมต้อง Decision Tree — คำตอบเชิงเปรียบเทียบ

| ประเด็น | 🌳 Decision Tree | KNN | Logistic Regression |
|---------|-----------------|-----|---------------------|
| ต้อง Scaling? | ❌ ไม่ต้อง | ✅ จำเป็นมาก | ✅ จำเป็น |
| จับ non-linear | ✅ ได้เอง | ✅ ได้ (แต่แพ้มิติสูง) | ❌ ได้แค่เส้นตรง |
| จับ interaction | ✅ ได้เอง จากการซ้อนกิ่ง | ⚠️ ทางอ้อม | ❌ ต้องสร้างฟีเจอร์เอง |
| อธิบายผลได้ | ✅ เป็นกฎ if-else | ❌ ไม่ได้เลย | ⚠️ ดูสัมประสิทธิ์ได้ แต่ตีความยาก |
| รับมือข้อมูลไม่สมดุล | ✅ มี `class_weight` | ❌ ไม่มี | ✅ มี `class_weight` |
| ความเร็วตอนทำนาย | ✅ เร็วมาก | ❌ ช้า ต้องเทียบทุกจุด | ✅ เร็วมาก |
| จุดอ่อน | Overfit ถ้าไม่ prune | Curse of dimensionality | สมมติฐานเส้นตรง |

### เหตุผลที่ DT ชนะ ไม่ใช่เรื่องบังเอิญ
ข้อมูลชุดนี้เข้าทางต้นไม้พอดี:
* ฟีเจอร์อยู่คนละหน่วยกันสุดขั้ว (บาทหลักหมื่น vs จำนวนเดือนหลักหน่วย)
* ความสัมพันธ์เป็นแบบ **มีเกณฑ์ตัด (threshold)** — "รูดน้อยกว่า 57.5 ครั้ง = อันตราย" ไม่ใช่ความสัมพันธ์เชิงเส้น
* มีตัวแปรหมวดหมู่ผสมกับตัวเลข
* มิติค่อนข้างสูง (20+ ฟีเจอร์) ซึ่งเป็นจุดตายของ KNN

### ข้อได้เปรียบที่สำคัญที่สุด: **อธิบายได้**
ทั้งสองเคสต้องส่งต่อให้ฝ่ายธุรกิจนำไปปฏิบัติ
Decision Tree ให้กฎที่**เอาไปตั้งเงื่อนไขในระบบ CRM ได้ทันทีโดยไม่ต้องรันโมเดล**
และเมื่อโมเดลตัดสินใจผิด เราตามสืบได้ว่าผิดที่กิ่งไหน
ในงานสถาบันการเงินที่ต้องอธิบายเหตุผลให้ลูกค้าและผู้กำกับดูแลได้ **นี่สำคัญกว่าคะแนนที่สูงกว่าเสียอีก**

## 8. 🎤 คำถามที่ TA น่าจะถาม — เตรียมคำตอบไว้

| คำถาม | คำตอบสั้น |
|-------|----------|
| "ทำไม Accuracy สูงแต่บอกว่าโมเดลไม่ดี?" | ข้อมูลไม่สมดุล ทายคลาสใหญ่อย่างเดียวก็ได้ Accuracy สูง ต้องดู Recall/F1 ของคลาสส่วนน้อย |
| "รู้ได้ยังไงว่ามี leakage?" | อ่าน data dictionary เจอสูตร แล้วเอาไปทดสอบกับข้อมูลจริง ตรงเป๊ะ 100% ทั้ง 10,127 แถว |
| "ทำไมไม่ scale ข้อมูลก่อนเข้า tree?" | tree เทียบ threshold ทีละฟีเจอร์ ไม่ได้คำนวณระยะทางข้ามฟีเจอร์ scale แล้วผลเหมือนเดิมเป๊ะ |
| "เลือก max_depth จากอะไร?" | 5-Fold CV บนชุด train เท่านั้น ไม่แตะชุด test จนกว่าจะวัดผลสุดท้าย |
| "ต้นไม้ลึก 12 ไม่ overfit เหรอ?" | ดูกราฟ tuning ประกอบ — เส้น CV พีคที่ 12 แล้วค่อยตก ถ้า overfit เส้น CV ต้องตกตั้งแต่ก่อนหน้านั้น และเทียบกับต้นไม้ไม่จำกัดความลึก (depth 19, F1 train = 1.0) ที่ overfit ชัดเจน ต้นนี้ดีกว่ามาก |
| "ทำไม Case 2 คะแนนแย่จัง?" | เพราะตัดฟีเจอร์รั่วออกหมดแล้ว พฤติกรรม Blue กับ Premium ทับซ้อนกันจริง ๆ ซึ่งก็คือคำตอบของโจทย์ ถ้าคะแนนสูงต่างหากที่ควรสงสัย |
| "ถ้าเป็นลูกค้าใหม่ที่ยังไม่มีประวัติรูดบัตรใช้ได้ไหม?" | ไม่ได้ เพราะฟีเจอร์ที่สำคัญที่สุด (`Total_Trans_Ct`, `Total_Trans_Amt`) ล้วนเป็นประวัติ 12 เดือน = ปัญหา **Cold Start** ต้องแยกโมเดลสำหรับลูกค้าใหม่ที่ใช้เฉพาะข้อมูลตอนสมัคร (อายุ รายได้ การศึกษา) |
| "ทำไมไม่ใช้ Random Forest?" | โจทย์กำหนดให้ใช้ Decision Tree และ RF จะเสียข้อได้เปรียบเรื่องการอธิบายเป็นกฎ if-else ซึ่งเป็นสิ่งที่โจทย์ธุรกิจนี้ต้องการ |
